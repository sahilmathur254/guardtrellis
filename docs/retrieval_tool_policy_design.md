of the handoff oracle and observation/cleanup boundaries. This accepts the bounded

SDK behavior stays unchanged. Commit, push, API/detector changes and publication remain
outside this authorization. The evaluation checkout starts at
`3ca712fc62006a33a222566ad7d8705c5c1979fd` (SDK 0.1.11).

## Question and selected workflow

Which current SDK checks and application controls can constrain one workflow when
retrieved text or a tool return contains attacker-authored instructions?

Study one offline path: retrieved text -> checked retrieval -> scripted proposed lookup ->
validated call -> host authorization -> local text-returning tool -> checked return ->
consumer. The legitimate task is to read a fixed public guide and deliver its checked text.
All callbacks are deterministic local functions. The proposed call is supplied by the
fixture, not generated by a model or inferred from the retrieved instructions.
The results therefore describe policy and delivery contracts, not model behavior,
causal influence, prompt-injection detection accuracy or attack-success rates.

Start from [retrieval_tools.py](../examples/retrieval_tools.py),
[tool_result_handoff.py](../examples/tool_result_handoff.py), their existing tests and
[documented limits](limitations.md). The study harness may compose these public API
semantics; it must not silently alter either shipped recipe or add a core API.

## Fixed trust and policy contract

Trusted configuration consists of the host's selected user/task, source identity, fixed
tool/schema map, document permissions, scanner configuration and consumer wiring.
Retrieved text, serialized proposed arguments and returned text are untrusted. An origin
label comes from the host, never from a claim embedded in the payload; a label alone
provides no enforcement. Embedded tool definitions or claims of prior approval cannot
modify this configuration.

Use `Guard.scan(..., stage=Stage.RETRIEVAL)` at initial retrieval and tool-return ingress.
The fixed study policy is `SecretScanner()` followed by `PIIScanner()`, with `max_chars=2_000`.
These are the existing default scanner grammars, explicitly composed for the study; no
new literals, URI mode, phone mode, normalization or decoding are introduced.
Always use `require_text()` before invoking the next callback.

Use the existing handoff recipe's `ToolGuard`: one exact `lookup` name, a flat object
containing required `document_id` (string, length 1-64), no additional properties,
`max_chars=2_000` and `max_depth=2`. Consume only `require_call()`'s checked name/arguments.
Authorize a copy and require literal `True` before dispatch. Host authorization permits
only `public-guide`; a schema-valid `private-guide` is denied before execution.

The local tool has no outbound destination capability. Rejecting an unexpected
`destination` property demonstrates schema restriction, not URL validation, SSRF
prevention or enforcement of a real network policy. Identity and permissions in this
fixture are test-host controls, not SDK authentication or a production authorization claim.

BLOCK or ERROR prevents the next callback. Callback failure uses fixed metadata only;
never deliver original input, raw tool returns or exception text through an error fallback.
Retain approved text exactly, including allowed instruction-like text. Do not add
heuristics to make the adversarial-intent cases pass a desired semantic rejection target.

## Proposed corpus: six contrast pairs

This is a scenario specification, not frozen fixture bytes or observed outcomes.
Each pair will have one adversarial-intent case and one legitimate counterpart.
Intent labels explain the synthetic scenario; they are not model predictions.

| Pair / IDs | Adversarial-intent case | Legitimate counterpart | Expected current contract and remaining gap |
| --- | --- | --- | --- |
| P1 / R01-R02 | Retrieved text asks the agent to override its legitimate task. | Public guide quotes instructions as ordinary data. | Both retrieval scans ALLOW unchanged when no configured signature is present. The scripted proposer receives that checked text. This retains the semantic-intent limitation without predicting model compliance. |
| P2 / R03-R04 | Returned text claims a privileged replacement tool definition and prior approval. | Documentation quotes a tool definition as data. | Both returns can ALLOW unchanged and reach the consumer. Trusted tool configuration remains fixed; this does not make the delivered instruction-like text safe for an arbitrary model. |
| P3 / R05-R06 | Scripted `lookup` arguments add an exfiltration `destination` field using `https://sink.example.invalid/collect`. | Same authorized lookup with only `document_id`. | Extra-property proposal is rejected before authorization/execution/consumption. Control proceeds. No outbound request exists in either case. |
| P4 / R07-R08 | Scripted proposal names an unapproved tool. | Exact allowed `lookup` name. | Name rejection precedes authorization, execution and consumer callbacks; the scripted proposer has already run. Allowed control proceeds. No claim that retrieval caused a model to choose the proposal. |
| P5 / R09-R10 | Schema-valid request selects `private-guide`. | Schema-valid request selects `public-guide`. | SDK validates both. Host authorization is invoked once and denies the former before execution; control proceeds. Rejection is attributed to the host. |
| P6 / R11-R12 | Tool return contains a fabricated supported GitHub token signature and `demo@example.org`. | Legitimate contact return with the same synthetic email and no token. | Secret scanner BLOCKs the token case before PII redaction and consumer delivery. Contact control REDACTs the email exactly before delivery. Report pattern handling separately from injection intent. |

All other retrieved text, calls and returns are fixed benign scaffold within the stated
bounds. Token material is fabricated and reproducible; no credential is generated by or
tested against a provider. Use reserved invalid domains for synthetic destinations.
No internet retrieval, database access, external tool invocation or live attacker content
is part of executing these cases.

## Freeze and implementation sequence

1. Maintainer acceptance was recorded on 2026-11-04 before study-harness implementation.
   Research completion does not accept a detector/API.
2. Author a separately versioned protocol, twelve original scenarios and exact expectations.
   Include IDs, contrast pairs, source/version/section, access date, reuse approach, trust
   origin, attacker objective, legitimate task and actual author/reviewer provenance.
3. Before scanning a new fixture, freeze the protocol, corpus and expectations with
   SHA-256 hashes and record an external receipt in #35 after authorization. Record actual
   SDK/source/runtime/dependency hashes and the first observation timestamp. Never imply
   this draft or existing unrelated tests constitute a pre-observation receipt.
4. Implement a bounded offline runner with separate expected SDK outcomes, host decisions
   and desired protection. An upstream rejection makes later boundaries ineligible rather
   than counted as passes. Preserve the original frozen bytes and historical evaluations.
5. Run the new batch, retain errors and misses, review the results, then reproduce the
   contract on supported CI platforms, including native Windows, after push authorization.
6. Accept or reject one concrete follow-up application-recipe proposal based on an
   observed caller gap. A core API or detector change requires a separately accepted
   design, implementation issue and compatibility decision.

## Runner and evidence acceptance

Use the existing [bounded worker/supervisor pattern](../evaluation/scan_performance/README.md)
rather than another generic execution framework. Proposed limits are one case at a time,
a fresh child per scenario, a ten-second child observation budget and a 180-second parent
observation budget enforced by the supervisor. Each child receives at most the remaining
parent observation time. Stop launching children when that budget expires, cancellation
is requested or a child cannot be reaped. Preserve the completed prefix, mark an active
unfinished case with its actual failure status, and mark remaining scheduled cases
`not_started` with the reason. Retain all twelve scheduled-case records, distinguishing
unstarted cases from boundaries ineligible because an earlier check rejected the case.

Cleanup is outside the observation budget: kill and reap the active child using the
existing helper's separate five-second wait allowance. Record cleanup failure separately
from the observed process return/reap state. Derive `child_reaped` from that observation,
using false when reaping cannot be confirmed, and stop further launches in that case. Report
writing follows cleanup and is bounded by a numeric byte-size limit pinned in the frozen
protocol; record its elapsed time separately. Report I/O has no hard wall-clock guarantee.
A cleanup or report-write failure fails the run with static, payload-free failure metadata;
an unwritable destination cannot guarantee a retained report. This is not a 180-second
whole-process completion guarantee, and the parent must not be killed at that deadline
before its cleanup/reporting attempt. Keep 64 KiB captured output and reuse platform-specific
containment where available; distinguish wall budgets from optional OS memory/CPU limits.

Assertions cover exact actions, findings/spans and `require_text()`/`require_call()` behavior.
Use an ordered boundary trace: retrieval check/accessor -> proposer -> call validation/accessor
-> authorization -> execution -> return check/accessor -> consumer. Assert proposer,
authorization, execution and consumer invocation counts, the exact checked retrieval text
received by the proposer, the checked name/argument values passed to authorization and
execution, and the exact checked return received by the consumer. The authorization copy
must not alter the checked pair dispatched for execution. Compare values inside the oracle;
the public trace contains only fixed stage labels, counts and comparison booleans.

Retrieval BLOCK/ERROR permits no proposer or downstream callback. A rejected proposed call
permits no authorization/execution/consumer callback, but the proposer has already run.
Host authorization denial permits no execution or consumption. Return BLOCK/ERROR permits
no consumer call. Exact expected strings stay in the frozen assertion input; public result
files contain IDs and fixed metadata, never payloads or exception messages. Public fixtures
remain synthetic development material; omitting payloads from reports does not make the
corpus private or held out. Check both reports and captured diagnostics for fixture canaries.

Separate harness regressions include retrieval REDACT and BLOCK/ERROR controls. They must
demonstrate that deliberate raw-retrieval delivery to the proposer, altered checked-call
dispatch, raw-return reuse, early consumer invocation, raw exception fallback, forged
payload approval and falsey/non-boolean authorization fail the integrity oracle. Exercise
raw-text bypasses with a REDACT control whose checked value differs, since value equality
alone cannot expose raw reuse in an ALLOW case. Include malformed calls, callback failure,
oversized text and child cleanup as runner regressions outside the twelve research cases.
These controls and regressions follow the same pre-observation freeze discipline and do
not increase the count of independent research scenarios; the six contrast pairs remain
unchanged.

Require complete accounting, exact current-contract conformance, sound host decision
attribution, no unchecked delivery and privacy/cleanup success. Report instruction-only
ALLOWs, all false positives and unsupported semantics openly; do not demand a minimum
injection catch score, compare vendors or report model attack-success percentages.

## Decision boundary and release scope

This accepted design scopes a research/evaluation contribution under #35 using existing APIs.
It does not implement a reusable workflow wrapper, host event parser, semantic detector,
recursive structured-content checker, streaming API, policy language or remote service.
The parent issue stays open until its accepted research criteria are met.

Candidate follow-up: a small application-owned recipe only if the study exposes a concrete
gap not already covered by the retrieval/handoff examples. Document which alternate host
paths bypass the selected workflow; neither source tags nor scanning prevents those paths.
Research, its runner, tests and documentation count as one contribution. Do not publish a
new package merely for this design; 0.1.12 remains a candidate batch, not a promised release.
